## 1. 物差し

### この段階の目的（何のためのUIか）

1. 体験仮説の合意形成（完成UIではない）  
2. 背骨: 1案件が引合→請求まで流れる  
3. 必須: ロール別ホーム＋案件詳細  

### 優先度

| 帯 | 役割・領域 |
| --- | --- |
| P1 | 営業SFA／施工／稟議／経理・請求／クイック発注 |
| P2〜 | 事務の厚い台帳・経費など |
| P3 | 総務・車両・安全の深い機能 |
| ➖ | 人事ポータル・勤怠・会計仕訳確定 |

### 採点軸（1–5）

| 軸 | 意味 |
| --- | --- |
| 業務適合 | シナリオの仕事と画面の意図が一致するか |
| 段階適合 | **今**磨くべきか（目的に合っているか） |
| 日常UX | 迷わず毎日使えるか（発見性・認知負荷・焦点） |
| モバイル | 主デバイス方針との一致 |

## 3. シナリオ群の診断

### A. 幹（E2E＋営業〜経理）— 優先して磨く

**良い**
- ポータル「自分宛」と待ち状態の可視化  
- ＋新規からの管理部報告（役割逆転の解消）  
- ES管理部の専用キュー  
- 施工のゲート／Blocked文言  
- 拠点長の承認Inbox  

**弱い**
- 営業・施工が戦略上スマホ主なのに、検証・デモがPC Hub中心  
- 案件パネルに「契約変更・解約・訂正」が常時並び、例外が日常UIを騒がしくする  
- 「台帳・登録」が能力の平置きで、管理部の「次にやるキュー」が見えにくい  
- ES管理部と経理のペルソナ切替が運用認知を要求する  

**判定**: 目的（通し合意）には十分。P1の日常使いやすさは未達。

### B. お客様相談室 — 設計の穴

カタログではSFA利用者だが、シナリオは営業近似。受電→顧客特定→対応履歴の専用導線がない。  
**判定**: 機能は🟡、UXは目的ズレ。薄い「受電ホーム」1枚でも置く価値あり。

### C. 総務・人事 — 今は磨かない

入口確認とSSO説明はスコープ制御として正しい。ここを赤点扱いで作り込むと目的外。

### D. 例外シナリオ（解約・赤伝・版重ね）

到達可能だが、頻度低の操作が案件パネルに常駐。  
**判定**: 例外は役割別キュー／必要なときだけ出す方が、役割体験方針に合う。

## 4. 投資順（目的×優先度）

| 順 | やること | 理由 | やらない |
| ---: | --- | --- | --- |
| 1 | 営業スマホ「今日の訪問→報告」 | 人数最多・P1・戦略の主役。**2026-09-26: ホームを訪問主役に再構成済**（机上折りたたみ・語彙翻訳） | PC台帳の見た目磨きを先にしない |
| 2 | ES管理部ホーム＝キュー中心 | 幹ハンドオフの主役 | CAPS全行の均等配置を増やさない |
| 3 | 拠点長承認Inboxの最短化 | 決裁体験に直結 | 歩合詳細UI |
| 4 | 相談室の受電ミニホーム（任意） | カタログ矛盾の解消 | 専用基幹化 |
| 5 | 例外操作を役割キューへ寄せる | パネル過密の解消 | 全例外をホームに並べない |
| — | 総務深いWF／人事本体／会計仕訳 | — | **今の目的外** |

## 6. 結論

今のHubは、**「シナリオで業務が成立することを見せる」** 目的には概ね成功している。  
**「各役割が迷わず毎日使う」** UXには、優先度P1の現場（営業スマホ・施工）と管理部キュー体験の磨きが先。  
総務・人事の薄さは失敗ではなく、優先度どおりの正しい省略である。
