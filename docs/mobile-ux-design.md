## 0. 結論

| 問い | 答え |
|---|---|
| スマホも GitHub 型でよいか | **よくない。** GitHub Mobile の移植（台帳カード＋Issue詳細＋Comment）は検証の結果、現場では直感的でない |
| では何を変えるか | **見せ方と語彙だけ変える。データ・履歴・連携はPCと同一**（同じ行を別の窓から見る） |
| スマホの入口は何か | オブジェクト（台帳・顧客）ではなく**ジョブ（今日やること・報告する・承認する）** |

## 1. これまでの思考の棚卸し

### 1-1. デバイスが変わっても捨てないもの（本質）

| 本質 | PCでの表現 | スマホでの表現 |
|---|---|---|
| データは1つ | 台帳の行（Issue） | 同じ行。ただし「仕事カード」と呼ぶ |
| 役割の仕事が最上段 | View（保存フィルタ） | ホーム「いまやること」 |
| いま誰待ちか | ⏳待ちバッジ | 同じ待ち表示（人の言葉で） |
| 記録は履歴へ | Comment＋タイムライン | 「報告」ボタン→チップ選択（結果は同じ履歴に載る） |
| Close は最後だけ | Status=Done ≠ Close | スマホからは Close させない（PCの管理部業務） |

### 1-2. GitHub 型がPCで効く理由（＝スマホで効かない理由）

| GitHub型の強み | 成立条件 | スマホの現実 |
|---|---|---|
| 一覧性（表・View・階層▶） | 横幅・大画面 | 幅390pxで表は破綻 |
| 高情報密度 | 腰を据えたデスクワーク | 移動中・現場・片手・数十秒 |
| Issue/Repo/Status の語彙 | 毎日触る管理部・事務 | 営業・施工には外国語（翻訳が必要） |
| 右パネル・ホバー | マウス | タップのみ・誤タップ |
| フリーテキストComment | キーボード | 現場で長文は書けない |

### 1-3. 旧スマホシェルの敗因（saad-github-hub.html 内蔵版）

- タブが「ホーム / 台帳 / 顧客 / Inbox」＝**場所の名前**。何をすべきか画面が教えてくれない
- カードに `[稟議]` `sfa#2201` `assignee:@me is:open` がそのまま出る
- 報告するには: カード→Issue詳細→スクロール→textarea→Comment（4手＋文章作成）
- 詳細画面に Repository / Parent / Sub-issues とGitHubの内臓が見える

## 2. スマホ設計原則（5つ）

1. **ジョブで入る** — 入口は「今日やること」「報告する」「承認する」。台帳・顧客は検索の奥に格納
2. **1画面1目的** — 次の一手を1つだけ大きく出す。一覧と詳細を同居させない
3. **親指ファースト** — 下部タブ＋下部固定アクションバー。タップ領域44px以上。重要ボタンは画面下
4. **語彙の翻訳** — Issue→仕事、Comment→報告・メモ、Status→進み、Inbox→通知、Blocked→準備中、ref番号は補足表示のみ
5. **入力は選ぶ→撮る→書く の順** — 結果チップ＋定型ひとこと＋任意メモ。3タップで報告が完了する
6. **顧客・物件の活動は到着から** — 今日の予定をタップ → **現場到着報告** → **活動報告**。期限タスク（見積提示など）は到着なしで報告可。施工の入場報告も同じ「到着」語彙

## 3. 画面構成

### 3-1. 下部タブ（全役割共通の骨格）

| タブ | 中身 | 対応するPC画面 |
|---|---|---|
| ホーム | 挨拶＋焦点一文／いまやること／**今日の予定（タップ→到着・報告）**／待ち状況 | ポータル「自分宛」＋カレンダー |
| 案件 | 検索＋担当案件カード（進みステッパー＋誰待ち）→案件詳細 | 案件台帳（自分View） |
| **＋（中央大ボタン）** | 行動ランチャー: **現場到着**／活動報告／写真／稟議／資材／顧客登録 | ＋ add an item |
| 通知 | 人の言葉の通知（承認された・準備OK・差戻し）→タップで該当へ | Inbox |
| メニュー | 顧客検索／使い方／設定／PC版の案内 | gnav の残り |

### 3-2. 役割差（レンズ）

| 役割 | ホーム最上段 | ＋の中身 | 見えないもの |
|---|---|---|---|
| 営業（星本） | **次の訪問**＋今日の訪問リスト（机上は折りたたみ） | 訪問報告・見積申請・顧客登録 | 案件番号・通達・マニュアル（ホーム外） |
| 施工（山本） | **いまの現場**＋このあと（準備中/着工OK） | 入場報告・写真報告・完了報告・資材 | 金額・原価・案件番号 |
| 拠点長（田中） | 承認待ちキュー（スマホ=承認特化） | （承認が主・起票は少数） | 台帳操作 |

### 3-2a. ホーム情報設計（2026-09-26 改訂）

目的: 「今日の訪問／現場が主役」。机上・通達・マニュアルで第一面を散らかさない。

| 原則 | 実装 |
|---|---|
| 1画面1目的 | 営業: 訪問リストのみ。施工: いまの現場のみ |
| 重複をやめる | 「いまやること」と「今日の予定」の二重表示をやめ、次の1件ヒーロー＋訪問リストに統合 |
| 机上は折りたたみ | 見積期限・差戻し・自分の申請・通達は `<details>` |
| 語彙 | ホーム／案件一覧に `sfa#` / `ringi#` / Blocked を出さない（人の言葉＋顧客名・住所） |
| 進捗の安心 | 訪問 `0/2 報告済み` チップ |

### 3-3. 案件詳細（スマホ版レンズ）

- ヘッダ: 顧客名主体（「佐藤 一郎さま — シロアリ防除」）＋電話・地図ボタン（現場ユース）
- 進み: 5点ステッパー（引合→商談→契約→施工→請求）— PCのStatusの翻訳
- 「次にやること」カード1枚＋下部固定の主アクション
- 履歴: 人の言葉で新しい順（「田中拠点長が値引きを承認」）。システム語を出さない

## 4. PCとの関係（重要）

```
        同じデータ（案件・行・履歴・待ち）
              │
   ┌──────────┴──────────┐
   PC = GitHub型          スマホ = ジョブ型
   台帳・View・パネル      今日やること・報告・承認
   管理部/事務/拠点長      営業/施工/移動中の拠点長
```

- スマホの「報告」は PC の同じ行のタイムラインに載る（逆も同じ）
- 承認・ゲート開通の連鎖ロジックは完全共有
- **どちらが正ではない。役割と場面で窓が違うだけ**
